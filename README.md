## 🎯 О проекте и назначение

В сетевом бизнесе кофеен и пекарен ежедневно возникает проблема разрыва между точками продаж и цехом/складом:
- Бариста путаются во времени подачи заказов или присылают заявки поздно ночью в чатах мессенджеров.
- Производство тратит часы на ручную сводку из разных таблиц и чатов.
- При доставке теряются позиции, а факт недовоза или повреждения десертов фиксируется на словах без доказательств.
- Руководство не видит общих потерь от списаний и брака.

**«Кофейня → Производство» решает эту цепочку «под ключ»:**
1. Кофейня формирует заказ по каталогу с контролем неснижаемых остатков строго до дедлайна слота.
2. Система мгновенно агрегирует заказы со всех точек в единую производственную сводку (по цехам: выпечка, кухня, кофе/зерно, упаковка/химия).
3. Производство собирает и отгружает накладные с фиксацией факта.
4. Экспедитор доставляет заказы по маршруту.
5. Кофейня осуществляет электронную приёмку с фотофиксацией расхождений (брак, порча, недовоз).
6. Администратор в реальном времени видит журнал расхождений и финансовые показатели.

## 👥 Ключевые роли и функциональность

В приложении реализовано переключение ролей в шапке (Header) с разграничением прав и фильтрацией данных:

### 1. Супревайзер / Бариста кофейни (`shift_supervisor`)
* **Формирование заявки**: выбор дня поставки и временного слота (Утро ☀️ / Вечер 🌙).
* **Каталог товаров с фильтрацией**: группировка по категориям (Кофе и чай, Выпечка и десерты, Молочная продукция, Сиропы и топпинги, Упаковка и расходники, Бытовая химия).
* **Контроль лимитов**: автоматический расчет остатков, предотвращение овербукинга.
* **Серверный таймер дедлайна**: точный обратный отсчёт до закрытия слота по серверному времени (МСК), защита от изменения времени на устройстве сотрудника.
* **Блокировка редактирования**: по истечении дедлайна заявка замораживается и передаётся в производство.
* **Приёмка поставок**:
  - Просмотр поступивших накладных со статусами.
  - Попозиционная приёмка с указанием фактического количества.
  - Фиксация расхождений: выбор причины («Недовоз», «Повреждение упаковки», «Порча/бой», «Недостача») + комментарий + прикрепление фото.
  - Формирование цифрового акта расхождений.

### 2. Оператор производства / ЦБП (`production_operator`)
* **Сводная матрица заказов (Aggregated Orders)**:
  - Выбор даты и слота отгрузки.
  - Мгновенная сумма потребности всех точек сети в разрезе номенклатуры и цехов.
  - Цветовая индикация статусов сборки по позициям.
* **Управление накладными (Waybills)**:
  - Генерация расходных накладных для каждой кофейни.
  - Корректировка отгруженного количества (если на складе не хватило позиций).
  - Смена статусов: `Сформирована` ➔ `Собирается` ➔ `Отгружена (в пути)`.
  - Печать накладных и экспорт в печатные формы.

### 3. Водитель-экспедитор (`driver`)
* **Мобильный путевой лист**:
  - Список точек доставки на смену с адресами и контактами управляющих.
  - Учёт типа автомобиля (с рефрижератором / стандартный фургон).
  - Отметка статуса выполнения рейса («В пути», «Прибыл», «Сдал груз»).
  - Фиксация времени доставки.

### 4. Администратор сети (`admin`)
* **Справочники (Directories View)**:
  - **Торговые точки (Кофейни)**: наименование, адрес, привязанное юрлицо, закреплённый цех/склад, ответственные сотрудники.
  - **Номенклатура**: наименование, артикул (SKU), категория, единица измерения (шт, кг, л, уп), статус архивации.
  - **Временные слоты (Slots)**: настройка времени дедлайна приёма заявок и планового времени доставки для утренних и вечерних поставок.
  - **Сотрудники и доступы**: список персонала, роли, телефоны, привязка к конкретным точкам или цехам.
  - **Цеха и склады**: кондитерский цех, обжарочный цех, кухня, центральный склад.
  - **Юридические лица и счета**: мульти-юридический учет (ИНН, КПП, ОГРН, банковские реквизиты).
  - **Водители и транспорт**: ФИО, телефон, госномер, модель авто.
* **Журнал расхождений (Discrepancies Audit)**:
  - Единый реестр всех зафиксированных инцидентов при доставке и приёмке.
  - Фильтрация по датам, точкам, причинам и этапам возникновения (производство / логистика).
  - Статусы урегулирования претензий.
* **Мульти-тенантность (Multi-Account)**:
  - Поддержка нескольких брендов кофеен/франшиз в рамках одной базы данных (например, «Арома Холдинг» и «Nordic Coffee Group»).
* **Инструменты симуляции (Dev Bar)**:
  - Тестирование поведения системы при наступлении дедлайна, проверка офлайн-режима и сброс тестовых данных.

## 🔐 Аутентификация и права доступа

Вход выполняется по email и паролю. Сессия хранится в `HttpOnly`-cookie (подписанный токен, 12 часов),
пароли — в виде хэшей scrypt. **Роль, аккаунт и привязки (кофейня, цех, водитель) сервер берёт из БД на каждом
запросе**, поэтому смена роли, архивация сотрудника или смена пароля действуют сразу.

**Первый запуск**

1. Задайте `AUTH_SECRET` (обязателен в production) и `BOOTSTRAP_ADMIN_EMAIL` / `BOOTSTRAP_ADMIN_PASSWORD`
   (см. `.env.example`).
2. Обновите схему БД (добавляется колонка `employees.password_hash`) и создайте администратора:
   `npm run ydb:schema && npm run auth:bootstrap` (при `YDB_AUTO_SCHEMA=true` сервер сделает это сам при старте).
3. Войдите, откройте «Справочники → Сотрудники» и заведите остальных: email, пароль, роль, кофейня/цех/водитель.
4. Удалите `BOOTSTRAP_ADMIN_PASSWORD` из окружения.

**Сброс пароля:** `NEW_PASSWORD='...' npm run auth:set-password -- user@company.ru`.

**Аудит слабых паролей:** `npm run auth:audit` показывает сотрудников с очевидными паролями (`1`, `12345678`, `admin`…),
`npm run auth:audit -- --revoke` сбрасывает такие пароли. Запустите, если на сервере когда-либо работала версия
с паролем `1` для `admin@aroma-coffee.ru`; после сброса задайте новые пароли через `auth:set-password` и смените `AUTH_SECRET`
(это завершит все ранее выданные сессии).

**Безопасность (кратко):** токен сессии живёт только в `HttpOnly`-cookie (`SameSite=Lax`), в JSON и `localStorage` он не
попадает; запросы на изменение данных принимаются только с того же хоста (или из `TRUSTED_ORIGINS` — точные origin);
встраивание в iframe запрещено. Для разработки в iframe (AI Studio) есть `ALLOW_EMBEDDED_PREVIEW=true`, но при
`NODE_ENV=production` он игнорируется. Значений по умолчанию для администратора нет.

**Деплой на Vercel.** Все запросы `/api/*` обслуживает одна функция `api/index.ts`; правило `rewrites` в `vercel.json`
передаёт ей исходный путь (`/api/auth/me` → `/api/index?__path=auth/me`, дальше путь восстанавливает
`src/vercel-url.ts`). Не заменяйте её файлом вида `api/[...path].ts`: в проектах не на Next.js Vercel создаёт для такого файла маршрут
только для одного сегмента (`/api/health`), а `/api/auth/me`, `/api/waybills/:id/receive` и другие вложенные пути получают 404
от платформы. После деплоя `https://<проект>.vercel.app/api/auth/me` без входа должен отвечать **401** (JSON), а не 404.

**Что разрешено ролям (проверяется на сервере)**

| Роль | Видит | Может |
|---|---|---|
| `admin` | всё в своём аккаунте | править справочники и сотрудников; всё остальное |
| `production_operator` | заказы и накладные своего цеха, водителей | формировать накладные, собирать и отгружать |
| `shift_supervisor` | свои кофейни, их заказы и накладные | оформлять заказы, принимать поставки |
| `driver` | только свои накладные и свой профиль | начинать рейс, менять статус своей смены |

Аккаунт компании определяется только сессией; заголовок `x-account-id` игнорируется. Пока нет UI создания
новых компаний: новый аккаунт создаётся через `BOOTSTRAP_ADMIN_ACCOUNT_ID`.

## ⏰ Учёт времени и дедлайны слотов

В ресторанном и кофейном бизнесе персонал часто работает с разных устройств (личные смартфоны, служебные планшеты), где локальное время может спешить, отставать или находиться в другом часовом поясе.

Система использует **серверный источник времени (`/api/time`)**:
1. Сервер возвращает текущее точное время по часовому поясу операционного центра (по умолчанию `Europe/Moscow`, UTC+3).
2. Клиентское приложение синхронизирует часы с сервером при старте и каждые 30 секунд.
3. В верхней панели всегда отображается индикатор:  
   `🕒 Серверное время: 23:45:10 МСК (UTC+3) · Дедлайн под контролем`.
4. При наступлении дедлайна слота (например, 00:30) заявка автоматически блокируется, даже если на телефоне бариста установлено 00:15.
5. При изменении времени дедлайна в справочнике администратора новые правила мгновенно вступают в силу для всех пользователей сети.

## 🛠 Стек технологий

* **Frontend**:
  - React 19 (SPA, хуки, модульная архитектура)
  - TypeScript 7 (строгая типизация всех сущностей)
  - Tailwind CSS 4 (адаптивная мобильная и десктопная вёрстка)

  - Node.js (v20+)

* **База данных**:
  - PostgreSQL (Cloud SQL или локальный сервер)
  - Drizzle ORM (типобезопасные миграции и запросы)
  - Пул соединений `pg.Pool` с кэшированием и автоматическим реконнектом
  - Встроенный механизм автоматического сидинга демонстрационными данными при первом старте

## 🚀 Установка и запуск на сервере

### Быстрый старт для разработки

1. **Клонируйте репозиторий**:
   ```bash
   git clone <URL_ВАШЕГО_РЕПОЗИТОРИЯ> coffee-erp
   cd coffee-erp
   ```

2. **Установите зависимости**:
   ```bash
   npm install
   ```

3. **Создайте файл конфигурации**:
   ```bash
   cp .env.example .env
   ```
   *(При разработке без локальной БД PostgreSQL сервер автоматически запустится со встроенным кэшированием).*

4. **Запустите сервер разработки**:
   ```bash
   npm run dev
   ```
   Приложение откроется по адресу `http://localhost:3000`.

### Развёртывание в Production (Node.js + PM2)

Это рекомендуемый и наиболее простой способ запуска на стандартном VPS/VDS сервере под управлением Ubuntu/Debian.

#### Шаг 1. Подготовка сервера и установка Node.js & PostgreSQL

```bash
# Обновление пакетов
sudo apt update && sudo apt upgrade -y

# Установка Node.js 22 LTS
curl -fsSL https://deb.nodesource.com/setup_22.x | sudo -E bash -
sudo apt install -y nodejs git postgresql postgresql-contrib

# Установка глобального менеджера процессов PM2
sudo npm install -g pm2
```

#### Шаг 2. Создание базы данных PostgreSQL

```bash
sudo -u postgres psql
```
В консоли PostgreSQL выполните команды:
```sql
CREATE DATABASE coffee_erp;
CREATE USER coffee_user WITH ENCRYPTED PASSWORD 'StrongPassword123!';
GRANT ALL PRIVILEGES ON DATABASE coffee_erp TO coffee_user;
-- Для PostgreSQL 15+ дайте права на схему public:
\c coffee_erp
GRANT ALL ON SCHEMA public TO coffee_user;
\q
```

#### Шаг 3. Клонирование и сборка приложения

```bash
cd /var/www
sudo git clone <URL_РЕПОЗИТОРИЯ> coffee-erp
cd coffee-erp
sudo chown -R $USER:$USER /var/www/coffee-erp

# Установка зависимостей
npm install

# Настройка .env файла
cp .env.example .env
nano .env
```
Заполните параметры подключения к базе данных в `.env`:
```env
PORT=3000
NODE_ENV=production
DISABLE_HMR=true
TZ=Europe/Moscow

SQL_HOST=127.0.0.1
SQL_PORT=5432
SQL_USER=coffee_user
SQL_PASSWORD=StrongPassword123!
SQL_DB_NAME=coffee_erp
```

#### Шаг 4. Сборка фронтенда

```bash
npm run build
```
Эта команда скомпилирует оптимизированные статические файлы фронтенда в каталог `dist/`.

#### Шаг 5. Запуск через PM2

Для запуска TypeScript-сервера в продакшене используйте встроенный рантайм `tsx`:
```bash
# Запуск процесса
pm2 start "npx tsx server.ts" --name "coffee-erp"

# Настройка автозапуска при перезагрузке сервера
pm2 save
pm2 startup
```

Проверить статус работы приложения:
```bash
pm2 status
pm2 logs coffee-erp
```

### Развёртывание через Docker / Docker Compose

Если вы предпочитаете контейнеризацию, создайте в корне проекта два файла:

#### `Dockerfile`:
```dockerfile
FROM node:22-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM node:22-alpine AS runner
WORKDIR /app
ENV NODE_ENV=production
ENV PORT=3000
COPY package*.json ./
RUN npm ci --omit=dev && npm install -g tsx
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/server.ts ./server.ts
COPY --from=builder /app/src ./src
COPY --from=builder /app/tsconfig.json ./tsconfig.json

EXPOSE 3000
CMD ["tsx", "server.ts"]
```

#### `docker-compose.yml`:
```yaml
version: '3.8'

services:
  postgres:
    image: postgres:16-alpine
    restart: always
    environment:
      POSTGRES_DB: coffee_erp
      POSTGRES_USER: coffee_user
      POSTGRES_PASSWORD: StrongPassword123!
    volumes:
      - pgdata:/var/lib/postgresql/data
    ports:
      - "5432:5432"

  app:
    build: .
    restart: always
    depends_on:
      - postgres
    environment:
      PORT: 3000
      NODE_ENV: production
      TZ: Europe/Moscow
      SQL_HOST: postgres
      SQL_PORT: 5432
      SQL_USER: coffee_user
      SQL_PASSWORD: StrongPassword123!
      SQL_DB_NAME: coffee_erp
    ports:
      - "3000:3000"

volumes:
  pgdata:
```

Запуск контейнеров одной командой:
```bash
docker compose up -d --build
```

### Настройка Nginx и SSL (Let's Encrypt)

Для открытия приложения по доменному имени (например, `erp.mycoffee.ru`) настройте Nginx в качестве reverse-proxy:

1. **Установите Nginx и Certbot**:
   ```bash
   sudo apt install -y nginx certbot python3-certbot-nginx
   ```

2. **Создайте конфигурационный файл сайта**:
   ```bash
   sudo nano /etc/nginx/sites-available/coffee-erp
   ```
   Вставьте конфигурацию:
   ```nginx
   server {
       server_name erp.mycoffee.ru;

       # Максимальный размер загружаемых фото расхождений (15 МБ)
       client_max_body_size 15M;

       location / {
           proxy_pass http://127.0.0.1:3000;
           proxy_http_version 1.1;
           proxy_set_header Upgrade $http_upgrade;
           proxy_set_header Connection 'upgrade';
           proxy_set_header Host $host;
           proxy_cache_bypass $http_upgrade;
           proxy_set_header X-Real-IP $remote_addr;
           proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
           proxy_set_header X-Forwarded-Proto $scheme;
       }
   }
   ```

3. **Активируйте сайт и перезапустите Nginx**:
   ```bash
   sudo ln -s /etc/nginx/sites-available/coffee-erp /etc/nginx/sites-enabled/
   sudo nginx -t
   sudo systemctl restart nginx
   ```

4. **Получите бесплатный SSL-сертификат**:
   ```bash
   sudo certbot --nginx -d erp.mycoffee.ru
   ```

## 📖 Руководство пользователя: сценарии работы

### Сценарий 1. Как бариста оформляет ежедневную заявку
1. В правом верхнем углу выберите роль **«Супревайзер / Бариста»** и вашу кофейню (например, *«Север Кофе (Петроградка)»*).
2. Выберите дату поставки (сегодня / завтра) и временной слот:
   - **☀️ Утро** (дедлайн заказа до 18:00 предыдущего дня, доставка к 09:00).
   - **🌙 Вечер** (дедлайн заказа до 00:30, доставка к 01:30 ночи).
3. Проверьте статус в информационном блоке:
   - Зелёный индикатор: `🟢 Приём открыт · До дедлайна осталось XX мин`.
   - Красный индикатор: `🔴 Дедлайн истёк · Заявка заблокирована для редактирования`.
4. Введите необходимое количество для требуемых позиций в каталоге товаров.
5. Нажмите **«Отправить заявку в производство»**. Статус заявки изменится на `Отправлена`.

### Сценарий 2. Как производство формирует сводку и накладные
1. Переключитесь на роль **«Оператор производства»**.
2. В разделе **«Сводный заказ»** выберите целевую дату и слот.
3. Система автоматически покажет суммарный заказ по всей сети:
   - Сколько килограммов эспрессо-смеси нужно обжарить и упаковать;
   - Сколько круассанов и десертов выпечь в кондитерском цехе;
   - Сколько упаковок стаканов и крышек подготовить на центральном складе.
4. В разделе **«Накладные»** нажмите «Сформировать накладные по точкам».
5. При сборке заказа комплектовщик может скорректировать фактическое количество (если позиция закончилась).
6. Нажмите **«Передать в доставку»** — накладная получит статус `Отгружена`.

### Сценарий 3. Как водитель доставляет заказы
1. Переключитесь на роль **«Водитель»**.
2. Откроется список кофеен по маршруту с указанием адресов и контактных номеров.
3. При выезде нажмите **«В путь»**, по прибытии к кофейне — **«Доставлено / Сдано на точке»**.

### Сценарий 4. Как кофейня принимает товар и фиксирует брак/недовоз
1. В роли **«Супревайзер»** перейдите во вкладку **«Приёмка поставок»**.
2. Найдите прибывшую накладную со статусом `Отгружена`.
3. Нажмите **«Принять поставку»**.
4. Сверьте количество привезенных позиций по факту:
   - Если привезли всё — оставьте значения без изменений и нажмите «Подтвердить приёмку».
   - Если круассаны помяты или не довезли молоко — измените графу «Принято», выберите причину (например, `Повреждено` или `Недовоз`), добавьте комментарий и прикрепите фото с телефона/камеры.
5. Нажмите **«Зафиксировать приёмку с расхождениями»**. Накладная сохраняется с актом, а инцидент автоматически отправляется в журнал претензий администратора.

### Сценарий 5. Как администратор настраивает время слотов и дедлайны
1. Переключите роль на **«Администратор»**.
2. Перейдите во вкладку **«Справочники» ➔ «Временные слоты»**.
3. В таблице слотов отображаются оба слота: Утренний (Morning) и Вечерний (Evening).
4. Нажмите **«Редактировать»** у нужного слота:
   - Укажите новое время дедлайна приёма заявок (например, `23:45`).
   - Укажите плановое время доставки (например, `01:00`).
   - Включите/выключите активность слота.
5. Нажмите **«Сохранить»**. Настройки сразу сохраняются в базу данных PostgreSQL и применяются для всех кофеен.

## 🔍 Диагностика и устранение неполадок (FAQ)

#### Вопрос: При входе пишет «Дедлайн слота истёк», хотя на часах компьютера другое время.
> **Причина**: На компьютере или телефоне бариста установлено неверное время или неверный часовой пояс.  
> **Решение**: Система ориентируется на серверное время (`/api/time`, по умолчанию МСК UTC+3), которое отображается в верхней панели сайта. Если требуется изменить время закрытия слота, администратор может изменить его в разделе *Справочники ➔ Временные слоты*.

#### Вопрос: После редактирования вечернего слота пропал утренний слот.
> **Решение**: Проблема устранена. В текущей версии справочник слотов гарантирует постоянное наличие обоих обязательных слотов («Утро» и «Вечер») с автослиянием из базы данных и защитой от перезаписи соседних записей.

#### Вопрос: Как сбросить систему к демонстрационным данным?
> **Решение**: Нажмите кнопку **«Сброс к демо-данным»** в нижней панели симуляции или отправьте POST-запрос:
> ```bash
> curl -X POST http://localhost:3000/api/reset
> ```
> База данных будет автоматически перенаселена тестовыми кофейнями, номенклатурой, заказами и накладными.

#### Вопрос: Как проверить статус работы сервера и базы данных?
> Выполните запрос:
> ```bash
> curl http://localhost:3000/api/health
> ```
> Ответ:
> `{"status":"ok","database":"postgresql","timestamp":"..."}`
